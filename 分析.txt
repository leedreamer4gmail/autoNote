去掉 corpseList.txt 缓存的可行性分析（2026-05-02）

=== 方案描述 ===

不再维护本地 corpseList.txt。
每次需要复活笔记时：
  1. 调 /notes/dead 获取最新尸体列表
  2. 取第一个 ID 复活
  3. 写入后再调 /notes/dead 验证该 ID 是否已消失（不再是 deleted=true）
     → 消失 = 复活成功；还在 = 复活失败

=== 结论：可行，推荐改 ===

优点：
  - 彻底消除缓存不同步问题（之前的 bug 根源）
  - 验证方式更可靠：直接问 Simplenote"你那边还有没有这个尸体"，比本地文件更权威
  - 代码大幅简化：去掉 corpseList.txt 文件、update_crops_list、remove_from_crops 三套逻辑
  - 前端刷新按钮也变简单：/crops 接口直接实时查，不需要先调 /notes/dead 再调 /crops 两步

缺点/风险：
  - 每次写入多一次 Simperium API 调用（获取尸体列表）。原来是 写+验证=2次，现在是 拿尸体+写+验证=3次。
    但 Simperium API 本身就在外网，增加一次影响不大。
  - 理论上有极低概率的并发争用（两个进程同时拿到同一个尸体 ID）。
    单用户场景下不可能发生，忽略。
  - 如果 Simperium /index 接口不稳定（502），写入前就会失败。
    目前已知 /index 比 /i/<id> 更稳定，可接受。

=== /crops 接口的变化 ===

去掉缓存后，/crops 接口直接调 Simperium /index?data=true，
过滤出 deleted=true 的笔记，返回 count 和 crops。
前端刷新按钮直接调 /crops，无需再区分"拉取"和"读缓存"两步。

=== 实施建议 ===

1. 删除 CROPS_FILE 常量和 corpseList.txt 相关的所有函数
2. /crops 接口：实时调 Simperium 返回
3. POST /note 写入流程：先调 /notes/dead 取第一个尸体 ID，再写入，再用 /notes/dead 验证
4. 验证逻辑：写入后等 0.8s，调 /notes/dead，若目标 ID 不在列表中 = 复活成功

=== 续：多用户并发冲突问题 ===

场景：Manus 和 Copilot 同时调 /notes/dead，都拿到了同一个尸体 ID，然后都往这个 ID 写内容。
结果：后写的那个覆盖先写的那个，先写的那个内容丢失。

是否需要维护列表 + 状态锁？

分析：

1. 本质是"分布式选号"问题。

   用本地文件锁（如 Python 的 fcntl/portalocker）只能防止同一进程内的并发，
   但无法防止不同 AI 客户端（Manus 直连、Copilot 通过 transNote、浏览器前端）同时发起请求。

   真正的原子选号需要：读取尸体列表 + 标记"占用中" + 写入 这三步在服务端原子执行，
   且在"占用中"状态期间其他请求拿不到这个 ID。

2. 实现方式：在 transNote 服务端加一个内存集合 `_claimed = set()`。
   - 选尸体时：从 /notes/dead 里过滤掉已在 `_claimed` 中的 ID，取第一个，立即加入 `_claimed`
   - 写入成功后：从 `_claimed` 移除（因为该笔记已不再是尸体）
   - 写入失败后：从 `_claimed` 移除（释放占用，下次重试）
   - 为防止僵尸占用（进程重启），`_claimed` 是纯内存的，重启自动清空

3. 这种方案相比"维护 corpseList.txt 文件"：
   - 不需要磁盘文件，没有磁盘 I/O 的竞态
   - 重启后自动清空，不会遗留"占用中"的脏数据
   - 仍然是从 Simplenote 实时拿列表，列表始终准确
   - 代码比本地文件锁简单，也不需要 filelock 依赖

4. 实际场景下，并发冲突是极低概率事件（写一篇笔记大约 1~2 秒，两个 AI 同时在这 1 秒内抢同一个 ID）。
   但如果要做就做彻底，加内存集合是最小代价的方案。

=== 最终推荐方案 ===

- 去掉 corpseList.txt
- /crops 实时查 Simperium
- 用内存集合 `_claimed` 做轻量原子占位（线程锁保护读-标记-返回三步）
- 写入后（成功或失败）均从 `_claimed` 移除
